# 第 2 章：仓库分层与包地图

> 本章导读：45 个 workspace 包怎么分组、各自承担什么架构角色、改动应该落在哪一层。本章是"地图"而非"机制"——机制在各专章。建议先读[第 1 章](01-cordis与组装.md)了解插件与组装词汇。

## 2.1 分层全景

```text
┌─────────────────────────────────────────────────────────┐
│ apps/         产品装配：cli（dsh bin 启动器）、web       │
├─────────────────────────────────────────────────────────┤
│ packages/     @deepseek-ai/dsh-* 能力包（见 2.2 分组）   │
├─────────────────────────────────────────────────────────┤
│ vendor/       Cordis 框架及框架插件的 vendored 源码      │
├─────────────────────────────────────────────────────────┤
│ python/       Python SDK 与单 exe 运行时                 │
│ native/       landlock-run（Linux 沙箱启动器，C11）      │
│ examples/     可运行的 cordis.yml 叶子（演示组合）       │
│ website/      部分文档的 VitePress 投影                  │
└─────────────────────────────────────────────────────────┘
```

构建顺序保证下层不依赖上层。pnpm workspace 把 `vendor/*`、`packages/*/*`、`apps/*`、`native/landlock-run`、`examples`、`python/sdk-runtime` 组织在一起；`examples` 和 `python/sdk-runtime` 只是依赖解析成员，不是构建目标。

## 2.2 packages/ 分组

包按 `packages/<group>/<pkg>/` 两层组织。下表按架构角色重排（非目录序）：

### 产品 API 主干（core）

| 包 | 职责 | ctx 键 |
|---|---|---|
| `core/session` | 仅追加 `SessionEvent` 日志与内存存储 | `ctx.sessions` |
| `core/system-prompt` | 提示词片段与工具 schema 的组装 | `ctx.systemPrompt` |
| `core/tools` | 作用域化工具注册表与带把关的执行流水线 | `ctx.tools` |
| `core/agent` | `Agent` 接口、活跃 agent 注册表、`agent/*` 事件 | `ctx.agents` |
| `core/agent-loop` | 实现 Agent 接口的默认驱动器 | `ctx.agentLoop` |
| `core/scope` | 按 agent 划分作用域的注册原语 | 库，无 ctx 键 |

**核心包也只贡献插件**：agent loop 不是内核，是 `ctx.agents.setFactory()` 注册的一个工厂。详见[第 4 章](04-核心循环.md)。

### 能力 seam 包（详见[第 7 章](07-工具系统与执行世界.md)）

| 组 | 内容 |
|---|---|
| `llm/` | LLM 词汇与服务定义 + deepseek/pi-ai 两个 Provider + retry + token-meter |
| `fs/` | 文件系统能力 + local/sandbox Provider + 观测策略 + 文件工具 |
| `shell/` | shell 能力 + bash/pwsh × local/sandbox Provider + bash/pwsh 工具 |
| `subprocess/` | 子进程能力 + 本地进程树 Provider |
| `terminal/` | 持久终端会话 |
| `sandbox/` | 沙箱 SD + 平台后端（bwrap/landlock/seatbelt/windows-acl）+ 策略 |
| `e2b/` | E2B 远程执行世界 POC（sandbox + fs/subprocess 适配器） |
| `lsp/`、`web/`、`skill/`、`compaction/`、`code-runtime/`、`mcp/`（MCP 客户端桥，把外部 MCP server 工具接到 `ctx.tools`） | 各自的能力 seam |
| `subagent/`、`workflow/`、`jobs/` | 编排能力 seam（[第 9 章](09-编排能力.md)） |

### 会话数据与上下文

`session/`（持久化 JSONL/SQLite、投影、标题、遥测、检查点策略）、`session-query/`（会话检索：逻辑语料库、有界读取、lineage、SQLite FTS5）、`context/`（请求上下文注入插件）、`spill/`（超大工具输出落盘）、`storage/`（非日志数据 KV）、`workspace/`、`attachment/`。详见[第 5 章](05-会话日志与持久化.md)。

### 交互与安全（详见[第 8 章](08-交互审批与安全.md)）

`interaction/`（审批、权限预设、命令、ask-user）、`hooks/`（Claude Code/Codex hook 桥 + wire 协议库）、`guard/`（循环卫生 + 工具超时）、`identity/`、`feedback/`、`schedule/`。

### 组合与行为单元

`bundle/`（base/web-app/headless 三个组合包）、`preset/`（按会话组装 agent 能力）、`todo/`、`plan/`、`goal/`、`extensions/`（agent 自我修改：检视/挂载自己的插件）。

### 应用支撑与对外接口（详见[第 10 章](10-应用与对外接口.md)）

`host/`（webserver、apiproxy、frontend-static 等宿主面）、`client/`（浏览器壳、connection、conversation 引擎、ui-* 模块）、`api/`（Typert RPC 网关 + remotes 装配）、`typert/`（类型图生成/加载/运行时）、`sdk/`（自有 JSON-RPC）、`acp/`（ACP 协议服务器）、`boot/`（app-boot 等启动胶水）、`web/`（注意：**web 访问能力 seam** 在 packages/web，Web 服务器在 packages/host/webserver——命名容易混淆）。

### 基础设施

`util/`（零依赖工具）、`test-support/`（llm-replay 等）、`runtime-diagnostics/`（包级 invariant 运行时契约宿主）、`settings/`、`credentials/`、`examples/`（演示组合包）。

## 2.3 host / client 双面

每个包理论上可以有两个"面"：

- **host 面**：Node 进程内运行的 Cordis 插件（绝大多数包只有这一面）；
- **client 面**：浏览器模块（`dsh-client-*`，主要是 UI），构建期产出自描述的 CJS factory，运行时由浏览器壳装配。

实践中绝大多数包只有 Host 面；Client 面仅 `packages/client/*`；`api/remotes` 是唯一同时拆分 Host/Client tsconfig 的特例。关键约束（构建期 purity gate 强制）：client 面包之间**不能直接 import 值**——跨包协作必须走 Cordis 服务。也就是说，浏览器里的插件树复刻了 host 的架构纪律：一切皆插件、服务通信、effect 可逆。

## 2.4 依赖纪律

仓库有几条影响全部分层的硬规则（根 AGENTS.md）：

- 每个包都是 `@deepseek-ai/dsh-<name>`；`@deepseek-ai/cordis` 是每个 harness 包的 peerDependency；
- ESM everywhere（`"type": "module"`）；跨包用包名导入，本地相对导入带 `.ts`；
- **注册即 effect**：一切贡献走 `ctx.effect()` / `ctx.on()`，`register()` 返回 disposer；
- **类型化事件用 declaration merging**：事件 map 可合并扩展；`SessionEventMap` 成员默认 required-on-read（见[第 5 章](05-会话日志与持久化.md)的版本机制）；
- **能力 seam 必须三角色齐全**：Service Definition / Service Provider / Consumer 一起设计，单个角色不成 seam；
- **插件，而不是改循环**：新行为挂到已记录的扩展点上；改 `agent-loop` 必须同步更新架构文档。

## 2.5 小结

仓库结构就是架构的物化：`vendor/` 是框架，`packages/core` 是产品 API 主干，其余 `packages/*` 是按 seam 组织的能力，`bundle/` 把能力叠成产品，`apps/` 只是入口。记住一个判断方法：**一个新功能应该放在哪，取决于它是 SD、Provider 还是 Consumer**——想不清楚这个问题，说明还没找到它该挂的 seam。下一章先看运行时的数据落点，然后进入核心循环。
