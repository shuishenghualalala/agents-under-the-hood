# 第 5 章：会话日志、投影与持久化

> 本章导读：会话日志是 dsh 的单一事实来源。本章回答：日志里到底有什么（SessionEventMap）、模型历史如何从日志投影（surface 机制）、持久化如何异步落盘并在崩溃后自愈、格式版本如何演进、以及压缩（compaction）如何在不改写日志的前提下缩小模型上下文。建议先读[第 4 章](04-核心循环.md)。

## 5.1 为什么用事件溯源

朴素方案是存"消息列表"：每个轮次结束后把消息历史整体写盘。问题是消息历史只是众多消费者之一——UI 要逐 token 回放、遥测要 usage、fork 要任意边界、压缩要替换区间、崩溃恢复要区分"完成"与"撕裂"。

dsh 的选择是**事件溯源**：`Session` 是一条仅追加的 `SessionEvent` 日志，模型消息历史从不单独存储，而是由 `deriveMessages()` 从日志投影。回放、fork、恢复、transcript、遥测、持久化全部消费同一事件流。配合[第 4 章](04-核心循环.md)的运行时不变量（请求 = 日志的纯函数），系统里不存在第二份事实来源。

## 5.2 日志里有什么：SessionEventMap

`SessionEventMap` 是可声明合并扩展的事件词汇（`packages/core/session/src/types.ts`）。核心 13 个成员分三类：

| 类别 | 事件 | 说明 |
|---|---|---|
| **surface 事件** | `user/message`、`assistant/message`、`tool/result` | 唯三能进入模型派生历史的事件，携带 `surfaceOp`/`sourceEventSeqs` |
| **结构事件**（本文分类） | `turn/start`、`turn/end`、`step/start`、`step/end`、`assistant/chunk`、`tool/call` | 轮次/步骤边界、原始流式 chunk、工具调用记录。官方只二分 surface 与 log-only，"结构事件"是本文为可读性作的归类 |
| **仅日志事件** | `request/header`、`request/context`、`todo/write`、`session/end-seed` | 重建所需但不进入模型历史 |

插件经 declaration merging 扩展词汇（compaction、goal、approval、hooks……都加了自己的事件；`agent/inbox/spliced` 也是 `core/agent` 包扩展的会话事件，不在核心 13 之内）。信封是 `{type, seq, time, data, ignorable?}`；`seq = log.length` 保证连续。

两个设计细节：

- **surface 身份由类型系统在编译期强制**：只有 surface 三事件能携带 `surfaceOp`/`sourceEventSeqs`（条件类型），非 surface 事件携带即编译错误。
- **`assistant/chunk` 保留原始流**：逐 chunk 入日志使回放与 UI 逐 token 保真；usage chunk 还是失败请求唯一的 token 记账记录。体积问题交给存储编码解决（见 5.4 的打包行），而不是丢弃数据。

### surface 投影

`deriveEventMessage()` 是逐节点的纯投影规则：`user/message` → user 消息；`assistant/message` → assistant 消息（空内容跳过）；`tool/result` → user-role 工具结果；其余 → null。

surface 支持两种 `surfaceOp`：`append` 追加节点；`{op:'replace', start, end}` 遮蔽 [start, end] 区间。`SurfaceManager` 校验 seq 连续性、replace 范围存在性、`sourceEventSeqs` 必须覆盖全部被遮蔽节点（即：替换者必须声明它取代了谁）。**replace 是压缩的基石**——见 5.5。

## 5.3 一条事件的完整路径

```text
产生    agent loop 调 session.append(type, data, surfaceIntent?)
接纳    校验（热路径零 IO）：
        · snapshotJsonValue 递归一次完成"读+校验无损 JSON+拷贝"
        · SurfaceManager.validateNext() 预校验 surface 规则
        · 禁止 append 重入；深冻结后推入日志，seq 连续
发布    同步 fire-and-forget 派发 session/event（监听器失败被隔离，
        不影响已提交的追加）
落盘    持久化插件把事件复制到逐会话控制器，固定批窗口批量写
        session/flush（parallel 事件）做持久性检查点
        session-checkpoint-policy 把 flush 缝进 llm/stream：
        模型请求发出前先 flush，保证请求前缀已持久
重建    恢复时：load → 版本/词汇/连续性校验 → 崩溃修复 →
        SessionStore.prepare({seed}) → deriveMessages() 按需投影
```

注意分层：`core/session` 只持有内存日志与投影规则，**刻意不做 IO**（SessionStore 的 JSDoc 明说 "Persistence is intentionally not implemented here"）。持久化是独立能力 seam：`ctx.sessionPersistence` 抽象服务 + JSONL/SQLite 两个可互换后端。持久化失败经 `agent/error` 上报，**绝不写成会话事件**——失败信息进日志会污染重建。

## 5.4 持久化后端与崩溃自愈

两个后端：

- **JSONL**（默认，写到 `$DSH_HOME/sessions/`）：连续同块 chunk delta 打包成一行存储记录（`text-chunks` 等，实测约 56× 行体积压缩），解码后还原为逐字相同的事件——打包只是物理编码。zstd frame 压缩；原子发布在 POSIX 用 `link()`+`unlink()`（不用 rename，防并发覆盖），Windows 经 koffi 调 `MoveFileExW(MOVEFILE_WRITE_THROUGH)` 做持久命名空间发布（Windows 无父目录 fsync 契约）。
- **SQLite**：用 Node 内置 `node:sqlite`，事件行 1:1 映射含 `ignorable` 列，单调整数 `SCHEMA_VERSION`。

**崩溃修复**：加载时发现开放的 `turn/start` 没有配对的 `turn/end`，不截断日志，而是追加合成的 `turn/end {reason: {kind:'interrupted'}}` 配平——`interrupted` 是唯一不由循环发出的轮次原因，一眼可辨。只丢弃撕裂的物理尾记录；仅对冷会话生效，活跃会话拒修。

### 版本机制

`SESSION_FORMAT_VERSION = 0`，单一单调整数，无 major/minor——"能否自动升级"是每一步升级器的属性，不该由编号形状预先承诺。bump 由写方决定，仅限结构变更。读规则按方向：

- 日志**新于**读者 → 拒绝（`SessionFormatUnsupportedError`，区别于损坏错误）；
- 日志**旧于**读者 → 经升级器链在内存中转换查看，仅实际续写时才持久转换（升级器链已设计但暂未实现——deferred 到首个真实 v0→v1 步出现；当前 v0 无旧版本，旧于读者暂按"无升级路径"拒绝）。

词汇增长走逐事件 `ignorable: true` 信封标记：**未知类型默认必需**——读者遇未知必需事件必须拒绝重建。这个默认方向是安全决策：遗忘标记只会过度拒绝（不便），默认 ignorable 则会静默恢复被掏空的会话（安全事故，比如丢掉审批记录）。（机制就位，但 v0 当前无生产者实际设置 ignorable。）

## 5.5 压缩：不改写日志地缩小上下文

模型上下文窗口有限，压缩不可避免。难点是：压缩不能破坏"模型可见 ⟺ 已记录"——摘要本身也得是日志的一部分。

dsh 的做法：**压缩不改写历史，而是追加一条带 replace surfaceOp 的 `user/message`**（摘要检查点），附 `compaction/start|summary|end` 三个仅日志事件：

- 被遮蔽的历史事件仍在日志里，只是 surface 投影把它们从派生历史中移除；
- transcript 读 append-origin 事件，因此人类记录不丢失；
- `compaction/start` 与 `end` 构成锁时间点（非排他容器——二者之间可插入无关注入，手动路径只重新验证 span）；崩溃中途的压缩表现为"有 start 无 end"的遗留锁，可区分"上个生命周期的死锁"与"当前正在压缩"。

三种触发（`packages/compaction/compaction-basic`）：

| 触发 | 挂点 | 语义 |
|---|---|---|
| pressure | `agent/pre-step` 串行监听 | 请求推导前用 `ctx.tokenMeter` 测量，超阈值则选范围压缩 |
| context-overflow | `agent/request-error` | 捕获 `CONTEXT_WINDOW_EXCEEDED`，绕过阈值强制压缩；仅当 surface 实际前进才返回 `{kind:'retry'}` 重试 |
| 手动 | `compactNow()` | 在 idle 任务中运行 |

摘要调用本身复用会话自身的 system/tools/消息前缀做一次性 `ctx.llm.stream()`（`llmStreamCall:true`）——复用前缀旨在命中提供方的 prefix cache（设计推断，官方文档未明说 KV cache）。区域边界必须保持工具 call/result 配对（切开的 tool-call 没有 result 会污染历史），但不保持整轮。

## 5.6 上下文工程的其余部分

- **请求上下文插件**（`packages/context/*`：time-context、agent-instructions、tmux-context、session-reference）：不直接触碰 LLM 请求，而是在 `agent/pre-step` 往日志追加 `source:{kind:'plugin', form:...}` 的 user 消息——遵守"模型可见 ⟺ 已记录"，上下文注入与压缩、回放天然兼容。
- **token-meter**（`ctx.tokenMeter`）：不在流上挂钩，而是**回放会话日志**计量——以 `assistant/message.usage` 为锚点（usage 计数互不相交是适配器契约，见[第 6 章](06-LLM能力层.md)）；当最近一次成功调用的规范请求信封匹配 `requestHeader` 且总量不低于启发式锚点时复用其 usage，否则对完整信封与表层做启发式重定价。
- **spill**：超大工具输出落盘为会话作用域私有文件（0700 目录），模型侧只见定位符+检索提示。
- **storage**：非会话日志数据（工作区记录等）的 KV 枢纽；后端拥有介质、domain 拥有语义（zod schema），写链先持久再更新内存再发变更事件。
- **投影注册表**（session-projection）：每域一个 `{init, apply, view}` 纯函数单元，框架订阅一次 `session/event` 驱动全部单元；变更流输出**全量值**（绝不增量）——转移廉价、消费方 last-wins。持久化投影缓存按 `(sessionId,key,ver,seq,val)` 行存 checkpoint，冷读走"缓存行 + 尾部重放 + 写回"阶梯。

## 5.7 设计取舍

**为什么核心不做 IO**：让"日志语义"（连续性、surface 规则、版本）与"存储机制"（JSONL/SQLite/未来的远程后端）各自独立演进；核心因此可以在纯内存里完成全部测试，无 key 快照回放（`DSH_SNAPSHOT=replay`）正得益于此。

**为什么保留原始 chunk 而不是只存组装后的消息**：回放/UI 保真、失败请求的 token 记账、以及"精确重计价"都需要原始流；体积是存储层的问题（打包行约 56× 压缩，实测值随数据变动），不该牺牲事件层的完整性。

**为什么崩溃修复是配平而非截断**：截断会丢失"崩溃前已完成的工作"的证据；追加合成 `interrupted` 配平既让日志重新合法，又保留了完整的事故现场。

## 5.9 小结

日志章的系统模型：**仅追加事件流是唯一事实；surface 投影派生模型历史；持久化是可替换后端；压缩是 replace 投影而非改写；版本与词汇增长都有明确的拒绝方向**。掌握了日志，就掌握了 dsh 一切"状态在哪"的问题。下一章看日志的生产者之一：LLM 能力层如何把各家线缆协议翻译成统一词汇。
