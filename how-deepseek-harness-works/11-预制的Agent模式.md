# 第 11 章：预制的 Agent 模式--一个进程里的四副面孔

> 本章导读：[第 9 章](09-编排能力.md)讲了 preset 的机制骨架--按会话挂载能力集合。本章讲发行版实际预制了哪几类 preset、它们各自为什么存在。四个模式不是平铺的四个选项，而是一条能力递增的链：极简 -> 标准 -> PTC -> 创造，每一环解决一个上一环没有的问题。读完你会理解：为什么"agent 模式"在 dsh 里是一等公民、host 与 preset 两层平面如何分工、这四副面孔的设计意图如何串联。建议先读[第 1 章](01-cordis与组装.md)（scope/isolate）与[第 9 章](09-编排能力.md)的 9.2 节。

## 11.1 为什么"agent 模式"是一等公民

多数 agent 工具是"一套固定能力"：工具表写死在代码里，想换就得改源码或重启。dsh 面对的是另一种场景--**一个进程、多个会话、各自不同的能力集合**。同一段进程里，可能同时跑着一个只会写代码的会话、一个能检索网页的会话、一个能改写自己运行时的会话。

如果能力集合是全局的，这些会话只能共用一份工具表，谁也无法独立做减法或做加法。dsh 的回答是把"一个 agent 拥有哪些能力"做成可挂载的单元：一个 **preset** 就是一份组合文件，挂在某个 agent 的 scope 上下文之下，只对那个会话生效；同进程的别的会话各自保持自己的组合，互不干扰。

这是"一切皆插件"在会话粒度的延伸。不只是"系统能换插件"，而是"每个会话能换自己的插件子集"。于是"模式"不再是开关，而是一等的数据：可列举、可切换、可复制、可自定义。发行版预制的四类模式，就是这套机制的开箱实例。

## 11.2 两层平面：host 与 preset

preset 能装什么、不能装什么，是这套设计的关键。有些东西天然是进程单例：工具注册表的索引、子代理注册表、模型路由、沙箱策略、持久化后端。若把它们放进 per-session 的 preset，两个会话就各有一份、彼此看不见--浏览器想跨会话列"所有后台任务"时就断了，因为没有一个进程级注册表可查。

所以 dsh 把组合分成两个平面：

```text
host 平面（进程级，所有会话共享一个实例）
  注册表本身、模型路由、沙箱与审批栈、持久化、子代理后端
        ↑ 工具行从这里解析后端
        │
preset 平面（会话级，挂在该 agent 的 scope 下）
  persona、提示词段、面向模型的工具行、按会话隔离的状态服务
```

一个工具行落在哪个平面，判据是"这个东西是不是只属于一个 agent"。shell 工具的执行器（沙箱、进程组）是进程共享的引擎，留 host；shell 工具的"模型面"（schema、描述）随会话变化，进 preset。子代理注册表要被浏览器跨会话查询，留 host；委派工具的模型面进 preset。一句话：**preset 选的是"这个 agent 能做什么"，host 管的是"做这件事的引擎只有一台"**。

这个划分不是 preset 独有的纪律--它就是 [第 9 章](09-编排能力.md)的 isolate realm 判据在产品层的落地。一个服务若是真正 per-agent 的（计划状态、压缩引擎、工作流引擎），就进 preset 的 entry-local realm，两个会话各跑各的；若是按会话键但跨会话读的（token 计量），就留 host，否则浏览器读到的上下文计量会随哪个 preset 挂着而漂移；若是进程单例（子代理注册表），更必须留 host。三类区分构成了 host/preset 划分的全部判断。

## 11.3 四类模式：一条递增的能力链

四个 preset 不是并列的四个预设，而是一条链：每个下游模式 = 上游模式 + 一个新维度。理解了上游，下游只需看"多出来那一维"。

| 模式 | 中文名 | 在上游之上加了什么 | 解决的问题 |
|---|---|---|---|
| minimal | 极简模式 | -- | 最小可用的编码助手，行为可预测 |
| standard | 标准模式 | 全套工具 + 压缩 + 计划/目标/子代理/工作流 | 全功能编码 agent |
| code | PTC 模式 | 代码呈现层（模型写程序组合多步） | 把五次往返压成一次 |
| cordis | 创造模式 | 自我修改工具 + 组合创作 skill + 双平面 persona | agent 能改写 agent |

递进逻辑很清晰：minimal 解决"最小可用"，standard 解决"功能完整"，code 解决"轮次效率"，cordis 解决"agent 能改 agent"。下面逐个看每副面孔的设计意图。

## 11.4 极简模式：一个可预测的底座

极简模式只给两个工具：一个持久 shell、一个文件编辑器，外加一段固定提示词，没有上下文压缩。它存在的理由不是"功能少"，而是"**可预测**"。

关键设计是 persona 的 `complete: true`：告诉系统"这段提示词就是完整的系统提示"，不让全局身份、运行时上下文快照、后续组装监听器再追加任何提示文本。于是这个 agent 看到的系统提示是固定的、可控的，不随部署环境抖动。运行时上下文快照也一并关掉--极简模式不向模型透露"你在哪个 harness 里跑"这类元信息。

为什么用持久 shell 而非一次性 bash？因为持久 shell 让命令状态跨调用保持（`cd` 之后的目录、导出的变量都在），对编码任务更顺手。代价是会话级的 PTY 服务要进 isolate realm，让两个极简会话各有各的终端栈，互不串台。文件系统同理走一个 entry-local realm，让本地裸文件系统只对这个 preset 的 agent 生效，影子般盖住 host 的沙箱文件系统。

为什么没有压缩？极简模式的典型对话短、上下文小，压缩是复杂度（replace surfaceOp、阈值触发、摘要回写），极简模式不背这层复杂度。它宁可对话长了直接截断，也不要一个隐式改写历史的机制。

一句话：极简模式是"去掉一切隐式行为"的编码助手--固定提示、固定双工具、无压缩、无元信息注入。

## 11.5 标准模式：默认的全功能态

标准模式是默认 preset。它在极简之上加回全套能力：文件与网页检索、skills、计划模式、目标、子代理、工作流、压缩、待办、向用户提问。但它加的方式很有纪律--全部只贡献"面向模型的那一面"，后端一律解析到 host。

这一节最有价值的是看 host/preset 两层在标准模式里如何具体落地。三类服务的归宿在此分明：

- **真正 per-agent 的状态服务**进 preset 的 entry-local realm。计划状态天然属于单个 agent（一个会话的计划不该被另一个会话看见），所以计划模式的服务进 realm 是正确生命周期，不是权宜。压缩引擎、工作流引擎同理--它们的生命周期就该绑死在 agent 上。

- **按会话键但被跨会话读的服务**留 host。token 计量器按 Session 键记账，但浏览器要为每个会话读它的上下文计量投影；若放进 preset realm，挂载哪个 preset 决定哪个会话能读到计量，其余会话的计量凭空消失。所以计量器留 host，preset 里的行通过 `ctx.get` 解析那一个实例。

- **进程单例**留 host。子代理注册表要被浏览器跨会话查询（列所有子代理），provider 名只能注册一次；若放进 preset realm，每个会话各注册一份，第二个会话就撞名。所以注册表留 host，preset 只贡献委派工具的模型面。

这套区分不是"能进 realm 就进 realm"，而是"看谁读它"。标准模式把这条判据用全了：凡是只有一个 agent 读的，进 realm；凡是跨会话读的，留 host。这也是为什么标准模式的组合文件看起来长--每一行都带着注释说明它为什么在这层、为什么不进 realm。那些注释不是啰嗦，是 host/preset 划分的判据留痕。

## 11.6 PTC 模式：把多步压成一步

PTC（Program-Tool-Composition）模式在标准之上只加一样东西：**代码呈现层**。理解它要先理解标准模式的一个效率痛点。

标准模式下，"读文件 -> 编辑 -> 读结果 -> 再编辑 -> 跑测试"是多次往返：模型每次只做一个动作，等结果回来，再决定下一步。每个动作都是一次模型请求，五次动作就是五次往返、五次推理开销。对于"我知道我要做这五件事"的情形，这种逐动作往返是浪费。

PTC 的思路是给模型一个"写程序"的能力。模型不再一次发一个工具调用，而是写一段 TypeScript 程序，程序里调用一个生成的 SDK，把多步操作编排进同一次执行。`run_code` 一次跑完这段程序，五个动作合成一次往返。代价是模型得会写这种程序、得理解 SDK 的函数签名--但对编码 agent 这正是它的强项。

为什么这是 preset 而非全局开关？因为"怎么用工具"是 per-agent 的呈现问题，不该影响别的会话。同一个进程里，native 会话（标准模式）和 PTC 会话可以并存，各自看到自己的工具目录。呈现层注册表本身留 host（调度器、API 代理的 presenter 都是它的消费者），preset 拥有的是"这个 agent 的工具如何呈现"--一行 `mode: code` 的配置。

一个细节体现 fail-loud 纪律：呈现层行会等待 host 的代码运行时服务，而不是假定它在。一个没装 TypeScript 运行时的部署，会让这个 preset 在挂载时就失败并点名是哪一行，而不是拖到第一次请求才出问题。**host 可用性本身不授予工具**--装了运行时还得在 preset 里把行启用，两层都要。

## 11.7 创造模式：agent 改 agent

创造模式（cordis）在标准之上加的是"自我修改"：一套能检视和挂载运行时插件的自修改工具、一个教组合创作的 skill、一段说明"编辑属于哪个平面"的 persona。它存在的理由是一个诱人的问题--**能不能让 agent 自己创作另一个 agent？**

这个问题在 dsh 里有了实质答案，因为"一个 agent 是什么"本身就是一份组合文件。agent 不是硬编码的，是 cordis.yml 挂出来的；那么 agent 读改这份文件，就是在读改另一个（或自己的）agent 的定义。自修改工具让 agent 能检视当前运行时的插件树、临时挂载一个插件做实验、再卸掉它。

但自我修改是信任边界，不是沙箱。这套工具能在活运行时上跑模型写的 JavaScript、能挂临时插件，而 agent 写出的组合会成为别的会话挂载的 preset。所以创造模式的 session 等同 shell 权限--工具自己的文档也这么声明。`trust` 字段的存在是为了让消费方（比如选择器 UI）能呈现这个区别，不是为了强制它；一个 user 信任的 preset 和 shell 访问同级。

persona 在这里承担了关键的教育职责。它用一段提示词告诉模型 dsh 的两个平面--host 放什么、preset 放什么、编辑该落在哪--并明确禁止改动随发行交付的预制 preset（升级会覆盖，且改坏 cordis preset 会废掉这个模式本身）。要改预制模式的行为，应该复制一份再改副本。组合创作 skill 也随这个 preset 走而非全局注册，因为它讲的是"本部署的两平面"，复制 preset 就带走这份知识。

创造模式是"一切皆插件"的终极致敬：agent 的运行时对自己也是一棵可读改的插件树。

## 11.8 设计取舍

**为什么预制模式用"整份复制"而非"继承加覆盖"。** standard、code、cordis 互为超集，看起来该用继承表达，但 dsh 选了整份复制--code 的组合文件里完整重复了 standard 的每一行，只末尾多一节。原因是继承会让一个 preset 的可读性依赖另一个：读 code 要同时脑补 standard，改 standard 会隐式波及所有"继承"它的 preset。整份复制让每个 preset 自包含、可独立阅读与编辑。代价是升级部署时复制的 preset 不随之更新--但这正是 bundle/patch 层（[第 1 章](01-cordis与组装.md)）该做的事：patch 层表达"标准加一个改动"，preset 层表达"一整副面孔"。两层各管各的粒度。

**为什么切换 preset 只允许空白会话。** 一个已经产生历史的会话若换工具集，日志里记录的工具调用就无法被新工具重放--新组合可能根本没有那个工具。这是产品规则而非机械限制，由网关在 wire 层强制（返回 `agent-preset-locked`）。空白会话可以自由切换，因为它还没有历史要负责。

**为什么 preset 文件是只读的。** Cordis Loader 会在插件自销毁时把当前树写回源文件（标记 disabled 再写回）。若不覆盖这个写操作，一个会话退出就会把所有会话共享的预制 preset 截断成空列表--第一次会话结束就废掉全部模式。所以挂载的子树把 write 覆盖成空操作：preset 是输入，从来不是持久化目标。作者改 preset 是另一次显式的文件操作，不经过这条写回路径。

**为什么 persona 用模板变量。** 身份文本里的 `{{model}}`、`{{cwd}}` 在挂载时从 agent 自己的路由和工作目录解析。这让一份 preset 文件不需要硬编码模型名或目录--同一个 preset 在不同工作区、不同模型路由下都成立，身份自动对齐。

## 11.10 小结

四个预制模式是 host/preset 两层划分的具体实例。它们形成一条能力递增的链：极简求可预测、标准求完整、PTC 求效率、创造求自指。四副面孔共享同一套底层注册表，只在"面向模型的能力子集"上分化。预制不是终点--用户可复制任意 preset 改出自己的模式，而那正是创造模式存在的意义。下一章看复刻这套架构的最小骨架需要哪些组件。
