# 第 7 章：工具系统与执行世界

> 本章导读：工具是模型唯一的手。本章回答：工具注册表与执行流水线长什么样、能力 seam 三角色模式为什么存在、"执行世界"共享为什么是远程执行的关键、以及一次 Bash 调用在本地/沙箱/E2B 三种形态下的完整路径。建议先读[第 4 章](04-核心循环.md)（工具调度在步骤内的位置）。

## 7.1 工具注册表与执行流水线

`ctx.tools`（`core/tools`）是作用域化工具注册表：`register()` 返回 disposer（注册即 effect）；`ToolRestriction` 支持 allow/deny 过滤继承来的工具（不约束本作用域自有注册）；`executionMode`（`exclusive`/`parallel`）供循环调度（见[第 4 章](04-核心循环.md)的工具调度）；`schemas()` 做白名单投影——`execute`/`timeoutMs` 等执行字段永远不进请求。

**工具定义**（`ToolDefinition`）= 模型面 schema + `output` 契约 + `execute` + 可选的 `finalizeContent`/`timeoutMs`/`isConcurrencySafe`/`presentCall`/`presentResult`。其中 **UI render intent 是设计的一部分**：`ToolCallView` 声明 `card: 'generic'|'terminal'|'diff'`（+`locations`），`ToolResultView` 另含 `search`/`read`/`web` 三种；presentation 方法是 `args` 的纯函数，流式与回放共用——UI 不需要懂任何工具的具体逻辑。

### 分阶段流水线

每次工具调用经过（`packages/core/tools/src/index.ts`）：

```text
tools/pre-execute (waterfall)   allow / deny / ask 把关
  → 单调守卫                     防"先拒后放行"之类的状态回退
  → tools/execute (waterfall)   环绕分派；超时/重试包裹这层
  → 工具体 execute()
  → tools/post-execute (waterfall)  结果加工（如 guard 的提醒注入）
  → finalizeContent             定义自己的结果定稿
  → tools/result                通知
```

[第 8 章](08-交互审批与安全.md)的审批、[第 4 章](04-核心循环.md)的调度都建立在它的约定上：**分派可并发，但 pre、结果提交与上下文保持模型序**。

## 7.2 能力 seam：三角色模式

dsh 的能力以 **seam** 组织，每个 seam 三种角色：

- **Service Definition（SD）**：声明 `ctx.<name>` 抽象服务与跨包词汇；
- **Service Provider（SP）**：实现它，按部署组合挂载，一个上下文一个（subagent 例外，是具名多 provider）；
- **Consumer**：通常是面向模型的工具包。

这个模式存在的理由：**SD 为所有当前 Consumer 设计，因此替换 Provider（本地 → 沙箱 → 远程）不改工具 schema、提示词与会话事件**。加一项能力意味着把三角色一并设计；单个角色不成 seam。

各 seam 速查表：

| Seam（ctx 键） | SD | Provider | Consumer |
|---|---|---|---|
| `ctx.fs` | `fs/fs` | fs-local、fs-sandbox、e2b/fs-e2b | tool-fs（read/write/edit）、tool-str-replace-editor（注：tool-fs-search 跑 ripgrep，是 ctx.subprocess 消费方，不在此列） |
| `ctx.shell` | `shell/shell` | bash-local/sandbox、pwsh-local/sandbox | tool-bash、tool-pwsh、hooks 桥 |
| `ctx.subprocess` | `subprocess/subprocess` | subprocess-local、e2b/subprocess-e2b | bash-local、bash-sandbox、terminal-bash、lsp-stdio、subagent-acp/codex/claude-code |
| `ctx.terminals` | `terminal/terminal` | terminal-bash | tool-terminal |
| `ctx.sandbox` | `sandbox/sandbox` | sandbox-local（bwrap/landlock/seatbelt/windows-acl） | bash-sandbox、pwsh-sandbox、terminal-bash |
| `ctx.lsp` | `lsp/lsp`（恰好 4 操作） | lsp-stdio | tool-lsp |
| `ctx.skills` | `skill/skill`（分层注册表） | skill-filesystem、skill-badge | tool-skill |
| `ctx.web` | `web/web`（search+fetch） | web-search-exa/perplexity/deepseek、web-fetch-http | tool-web |
| `ctx.credentials` | `credentials/credentials`（引用≠值） | credentials-local | llm 适配器 |

## 7.3 "执行世界"共享：远程执行的关键

这是全仓库最重要的分布式设计之一。**`ctx.fs` 与 `ctx.subprocess` 共同定义一个执行世界**：挂载在一起的两个 Provider 必须描述同一个路径命名空间、可执行文件集、进程与终端会话（这是 SD 上的明文约定）。

推论：高层能力（bash、PTY、LSP）只消费这两个接口，不点名 Provider。换成远程后端时它们**零改动随迁**——E2B POC 实证了这一点：`tool-bash`、`terminal-bash`、`lsp-stdio` 没有任何 E2B 专用 fork，组合一份 overlay（disable subprocess-local/fs-local，insert e2b 三件套）就把整个执行世界搬到了远程沙箱。

fs 接口为跨能力坐标提供三个"逃逸口但不出卖身份"的方法：`processPath(target)`（该世界内子进程可打开的规范化绝对路径）、`fileUrl(target)`（执行平台语法的 `file:` URI）、`contains(parent, child)`。`targetKey`/`FsVersion` 是 branded 不透明 id，消费方禁止解析——**不透明 id 是跨世界的防伪标记**。

## 7.4 生命周期：一次 Bash 工具调用

### 本地路径（逐行验证）

```text
1. tool-bash execute()
   · 校验参数；带沙箱能力的执行器经 ctx.sandboxPolicy.resolve({session})
     得逐调用策略
   · sandbox_permissions + justification 走 ctx.approval 提权审批（见第 8 章）
   · ctx.shellEnv.collect() 取 DSH_* 环境快照
2. ctx.shell.resolve(request) → 完全解析的 ShellExecSpec
   （bash-local：补默认 workdir、clamp 超时）
   ——"包边界显式优于隐式"的 request/spec 模板
3. ctx.shell.run(spec)
   bash-local 拼 ['bash','-c',command]，组装 SubprocessSpawnSpec
   （stdio collect 模式：内存尾部 + spill 文件；env 叠加序：
   ENV_OVERRIDES < 调用方 env < dshEnv），调 ctx.subprocess.spawn
4. subprocess-local
   凭据清洗的父环境 + detached 进程组 spawn；
   POSIX 信号发给进程组；Windows 树杀用 taskkill /T /F；
   terminate() = SIGTERM → graceMs → SIGKILL
5. CollectedOutput（尾部文本 + truncated + spillPath）回填，
   渲染 [exit code: N]
```

### 沙箱变体：argv 包装

bash-sandbox **继承** bash-local，仅在执行边界把 argv 换成 `ctx.sandbox.confine(argv, policy).argv`——纯函数式地返回 `[runner, profile..., '--', ...argv]`。runner 按平台：Linux bwrap→landlock（`native/landlock-run`：约 300 行 C11 "先限自身再 exec" 启动器，fail-closed）、macOS Seatbelt、Windows ACL 受限令牌。

结算后按两组正交的 stderr 签名分类：**denial 方言**（内核拒绝：bwrap=EROFS、landlock=EACCES、seatbelt=EPERM）与 **runner 失败**（runner 自己跑不起来，抛 `SANDBOX_UNAVAILABLE`）。无可用后端时 **fail-closed**——绝不静默退化为无隔离执行。

### E2B 变体：整个世界搬过去

`ctx.e2b` 在构造时开始建远程沙箱、建共享 cwd 与 runtimeRoot。`subprocess-e2b` 的 `spawn` 经 E2B Commands API 执行、轮询活跃度，`resolveExecutable` 用远程 `command -v`；`fs-e2b` 经 E2B Filesystem API 实现原子写/版本守卫。**bash 工具、bash-local、terminal-bash、lsp-stdio 全部不变**——它们只看见同一个 `ctx.fs`/`ctx.subprocess`。

overlay 注释里有一条"一世界不变式"：e2b.cwd、sandbox-policy.workspaceRoot、bash 默认 workdir 必须同名，否则进程落在远端而 bash 默认目录落在宿主——世界共享的代价是组合者要保证坐标一致。

## 7.5 策略与把关

**fs 策略用事件而非服务**：`fs/write-intent`、`fs/edit-intent` 是单槽 waterfall（先到先得不调 next()），`fs/observed` 是即发即弃记录。fs-observation-policy 不注册任何服务，只挂事件，用 `WeakMap<owner, Map<targetKey, FsObservation>>` 实现"先读后写"（owner 从事件 actor 推导，通常是 session，且从不读取其字段；edit 未见 → `FS_NOT_OBSERVED`）。工具只 dispatch 事件，**移除策略插件不破坏工具**。

**fs 沙箱是进程内栅栏，非内核边界**：fs-sandbox 只做 canonicalize-then-contain（路径规范化后检查包含关系），抛结构化 `FS_SANDBOX_DENIED`——可信进程内的路径围栏归 fs，不可信代码的内核级隔离归 bash 侧沙箱。两者共用 `writableRoots()`，保证围到同一个根。

**逐调用策略**：`SandboxExecutionPolicy` 每次调用解析（批准的模式 > 会话 `sandbox/mode` 事件 > 部署默认），使并发会话与一次性提权重试共存于同一 Provider。

## 7.6 设计取舍

**为什么沙箱是 argv 包装而不是 syscall 拦截**：消费方交出即将 spawn 的确切 argv，runner 以内核机制执行——harness 进程自身不受限，被包装进程及其后代跨 execve 继承限制。argv 包装让同一 seam 覆盖四个平台的 runner，且**消费方持有分类方言**（denial vs runner failure 是正交的）；ptrace/seccomp 注入式拦截既不跨平台也不易 fail-closed。推论：容器/microVM/远程执行**不是** `ctx.sandbox` 的 Provider，而是 fs/subprocess seam 的同级实现（E2B 正是这样切的）。

**为什么 fs 与 subprocess 共享世界**：远程编码世界只有在文件操作、命令、终端、语言服务器共享同一沙箱身份时才有用；否则每个远程后端都要复制一份 PTY/LSP 浅适配器，而"每个能力一个沙箱"会丢失文件/进程的身份一致性。

## 7.8 小结

工具系统的系统模型：**注册表是作用域化的、流水线是三个可改写 waterfall 加守卫与定稿的、能力是三角色 seam 的、执行世界是 fs+subprocess 共享的**。其中"世界共享"是最值得带走的设计：它让"远程执行"从产品特性退化为一次组合选择。下一章看悬在工具之上的安全层：审批、权限与纵深防御。
