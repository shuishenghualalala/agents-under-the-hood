# 第 4 章：核心循环——轮次、步骤与事件

> 本章导读：这是整个系统的心脏。读完你将理解：turn/step 的确切语义、inbox 如何把"用户输入、steering、注入上下文"统一成数据流、三个事件域的分工、一次完整轮次的每个阶段、以及为什么每个决策点都是 waterfall。建议先读[第 1 章](01-cordis与组装.md)了解事件模式与插件词汇。

## 4.1 核心循环解决什么问题

一个 coding agent 的运行本质是递归：用户输入 → 模型请求 → 工具调用 → 把结果喂回模型 → 再请求……直到模型不再调用工具。工程上的难点不在递归本身，而在：

- 用户可能在任何时候插话、打断、改主意（steering / cancel）；
- 模型请求可能失败需要重试，重试决策本身应该可审计；
- 每个决策点都应该可被插件拦截（审批、压缩、上下文注入、重放测试）；
- 崩溃恢复后，进行中的工作要能精确重建。

dsh 的回答是：**把循环落到一条事件溯源的日志上，并把每个决策点暴露为插件事件**。循环本身（`core/agent-loop`）也只是一个插件——它实现 `core/agent` 声明的 `Agent` 接口，经 `ctx.agents.setFactory()` 注册。理论上你可以换掉整个驱动器而不动任何工具。

## 4.2 turn 与 step 的确切语义

- **步骤（step）** = 一次模型请求 + 该请求触发的全部工具执行。持久边界是 `step/start` / `step/end`。
- **轮次（turn）** = 零个或多个步骤。轮次在**领取首条输入之前**打开（`turn/start` 先于 claim 与 pre-step），在"不再欠任何工作"时关闭：无存活工具调用、无新鲜 steering、next-step inbox 排空。

两个反直觉但深思熟虑的细节：

1. **轮次先于领取打开**。被 pre-step 拒绝、或首批输入被改写为空的轮次，仍会作为不含任何 step 的轮次持久关闭——日志因此记录了"这次尝试"，审计链没有暗门。
2. **turn 有编号且在 driver 存活期内连续**；`turn/end` 携带原因：`completed | aborted | blocked | error | max-tokens | interrupted`。其中 `max-tokens` 是粘性的（一旦某步触顶，后续正常完成的步骤不得把结论降级为 completed），`interrupted` 从不由循环自己发出——它仅供持久化后端在加载时关闭崩溃留下的孤儿轮次（见[第 5 章](05-会话日志与持久化.md)）。

## 4.3 三个事件域

dsh 把事件分成三个域，选对域是大多数改动的第一个决定：

| 事件域 | 性质 | 例子 | 何时用 |
|---|---|---|---|
| **会话事件** | 持久事实：仅追加进日志，并同步经 `session/event` 广播 | `turn/*`、`step/*`、`user/message`、`assistant/*`、`tool/*` | 某个事实在重载后必须仍存在 |
| **Agent 事件**（`agent/*`） | 实时、携带活跃 `Agent`，按 agent 作用域过滤 | `pre-step`、`request`、`turn-stopping`、`inbox/*`、`status` | 观察或拦截进行中的工作 |
| **能力事件** | seam 上的策略/适配器挂点，无需 import 循环 | `llm/stream`、`tools/*`、`fs/*` | 给某个能力附加策略 |

其中 `agent/pre-step`、`agent/request`、`llm/stream`、`tools/pre-execute`、`tools/execute`、`tools/post-execute` 是 **waterfall**：监听器必须调 `next()` 委托下去，直接返回即短路内建行为。`agent/turn-stopping` 是 serial（无 `next`）——因为轮次是否继续由 **inbox 里的数据** 决定，监听器顺序不应该能影响结局。（说明：官方架构文档把能力事件举例为 `fs/*`、`tools/*`、`telemetry/*`，未明列 `llm/*`；本文把 `llm/stream` 归入能力域是推断——它确属 llm seam 的事件。）

## 4.4 Inbox：一切输入都是数据

输入经同一个 inbox 到达驱动器。`Inbox` 是两条有序待处理列表（`next-turn` 与 `next-step`）的**持久投影**：

- inbox 走双通道：`agent/inbox/spliced` 是**持久全量快照**（重建队列用），先落日志再改内存投影——**持久先于投影**，崩溃恢复后队列不丢，UI 可以纯从日志重建队列；而 `agent/inbox/inserted`、`claimed`、`discarded` 是 agent 域的 **emit 逐条实时通知**（不入日志），供 UI 即时反映。
- `Agent` 句柄上的三个入口对应三种语义：
  - `followup(msg)` → next-turn + 唤醒：独占开启一个新轮次；
  - `steer(msg)` → next-step + 唤醒：汇入当前/最近一个步骤边界；
  - `inject(msg)` → next-step + **不唤醒**：注入的上下文留在 inbox 里，直到另一条消息唤醒驱动器（空闲时）或在下一个步骤边界被领取（运行中）。因此 inject 可能错过已领取批次的请求——这是明示语义，不是缺陷。

为什么双列表？因为"独占一轮的提示词"和"步边界汇入的输入"是不同的调度语义：followup 要等当前轮次彻底结束，steer/inject 则要在最近的步边界生效。

## 4.5 一次完整轮次的生命周期

以 `agent.followup(msg)` 为入口，全部发生在 `ReactLoopAgent`（`packages/core/agent-loop/src/agent.ts`）内：

```text
turn/start                          ← 先开轮，再领取
  │
  ├─ 1. claim：领取全部 next-step 输入 + 轮次边界上一条 next-turn 消息
  ├─ 2. 组装提示词片段与工具 schema（ctx.systemPrompt.assemble）
  ├─ 3. 动态运行时上下文投影为候选 user/message（仅快照变化时）
  ├─ 4. agent/pre-step (waterfall)：监听器返回 reject 或 enter(messages)
  │      reject          → turn/end {blocked}，批次终结（不丢弃、不重发）
  │      首个 enter 为空 → turn/end {completed}，不花模型调用
  │
  ├─ step/start
  ├─ 5. 每条 enter 消息追加为 user/message（持久）
  ├─ 6. buildRequest：
  │      deriveMessages() 从日志投影模型历史
  │      agent/request (waterfall)：可替换冻结的 LlmCallConfig（但不能改消息）
  │      ctx.llm.prepareCall 物化适配器默认值
  │      request/header（initial/resume/change 三态）与 request/context 写入日志
  ├─ 7. preparedCall.stream() → llm/stream (waterfall) → 适配器
  │      逐 chunk：session.append('assistant/chunk') + 喂 BlockAssembler
  ├─ 8. 失败：step/end 后派 agent/request-error (waterfall)
  │      某监听器返回 {kind:'retry'} 且不调 next() → 重试整个 buildRequest
  │      否则抛 LlmError 成为轮次错误
  ├─ 9. 成功：追加 assistant/message（usage + sourceEventSeqs 指回全部 chunk）
  ├─ 10. 工具调度（见下）
  ├─ step/end
  │      工具欠下一次请求 或 next-step 有输入 → claim → 下一个 step
  │
  ├─ agent/turn-stopping (serial)：异议者通过 agent.steer() 写数据表达
  │      之后重读 inbox——有新鲜 steering 就再跑一步，没有才收轮
turn/end {reason}
```

### 工具调度（步骤内的子循环）

`executeToolCalls()` 按每个工具的 `executionMode` 分类：

- `exclusive` 工具构成屏障（前后的 parallel 调用不会越过它）；
- `parallel` 工具进有界滚动池（默认上限 10）；启动前**重新分类**后续调用——注册表热变更立即生效。

每个调用走 `ctx.tools` 的分阶段流水线：`tools/pre-execute`（allow/deny/ask）→ 单调守卫 → `tools/execute`（超时/重试包裹这层）→ 工具体 → `tools/post-execute` → `tools/result`。关键性质：**分派可并发，但 pre、结果提交与上下文保持模型序**（结果提交只跨越连续就绪的槽位）。每个结果追加 `tool/result`；工具结果带的 `additionalContexts` 排入 next-step inbox，成为下一步的 user/message。

反向控制也是数据：工具结果带 `concludesTurn` 则该步直接收轮——"提前结束工具循环"不是控制流特例，而是工具结果的一个字段。

### 取消与唤醒

`cancel(cause)` 清空 inbox（除非 `keepInbox`）并 abort 当前 phase。abort 时已启动的工具调用排空提交、未启动的补记合成错误结果——**回放仍然合法**。唤醒闩锁保证"abort 后到达的唤醒"在收敛到 idle 后必定开新轮，不会丢消息。

## 4.6 "模型可见 ⟺ 已记录"的运行时不变量

这是整个架构最重要的不变量，值得单独一节。`agent-loop` 有一个不变量伴生插件，prepend 监听 `llm/stream`，对每次请求现场断言（`packages/core/agent-loop/src/invariant.ts`；它经 `ctx.invariants.register` 注册到通用不变量注册表，官方架构文档背书"由一项运行时不变量断言这一点"）：

- 请求已冻结（agent-loop 构建的请求深冻结后才发出）；
- `options.messages` 与 `session.deriveMessages()` 的 JSON **逐字节一致**；
- 与 fold 出的 `request/header` 一致。

也就是说，**每次模型调用都现场证明"请求是日志的纯函数"**。推论：新增一项模型可见输入 = 新增一个会话事件（扩展 `SessionEventMap` 并从日志渲染）——没有第二条通道。这就是为什么 `agent/request` waterfall 故意不能改消息：模型可见内容必须走已记录的通道。

## 4.7 设计取舍

**为什么 pre-step/request/tools 用 waterfall**：这些场景都是"一条插件链加工一个值、或包裹一次操作"。waterfall 让每个监听器既可改造值又可完全接管；`turn-stopping` 用 serial 则因为结局由数据决定。事件模式的选择就是在回答"这个决策点的结果由谁决定"。

**为什么轮次先于领取打开**：被拒绝/清空的尝试也留下持久轮次，日志即审计。朴素方案是"先领取再决定开不开轮"，但那会让 pre-step 拒绝成为一次无痕操作。

**为什么 inbox 是持久投影而不是内存队列**：(1) 崩溃恢复后排队的工作不丢；(2) UI 纯从日志重建；(3) "被拒步骤的输入"与"被丢弃的输入"在日志上可区分（claim 用纯删除 splice，由循环逐条发带 turn 坐标的 `claimed`）。代价是所有 inbox 操作都要过日志——但日志 append 是纯内存操作（落盘是异步的，见[第 5 章](05-会话日志与持久化.md)），热路径零 IO。

**取消即数据**：cancel、steer、inject 全部落到 inbox/abort 语义而非控制流 hack，使得并发场景（用户打断 + 工具在跑 + 新消息到达）有确定性的汇合点。

## 4.9 小结

核心循环的系统模型：**turn/step 是持久边界，inbox 是持久投影，每个决策点是 waterfall 事件，每次请求被不变量证明是日志的纯函数**。这四个性质合起来，使 dsh 的循环同时是可扩展的（插件在每个点介入）、可恢复的（崩溃后精确重建）、可审计的（日志记录一切包括被拒绝的尝试）、可测试的（无 key 快照回放）。下一章深入日志本身：它如何投影出模型历史、如何落盘、如何在崩溃后自愈。
