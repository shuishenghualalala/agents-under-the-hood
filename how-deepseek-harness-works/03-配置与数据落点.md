# 第 3 章：Harness Home 与运行时数据落点

> 本章导读：dsh 运行时在磁盘上读写什么、放在哪、为什么这样分。本章很短，但排查问题（会话丢了？配置没生效？凭据从哪来？）时它是第一站。建议与[第 1 章](01-cordis与组装.md)的组装机制对照阅读。

## 3.1 Harness home

`$DSH_HOME` 环境变量未设置时取 `~/.dsh`（`packages/util/home-paths`）。目录职责（源码验证）：

```text
$DSH_HOME/
├── cordis.patch.yml          # home 级用户 patch 层（优先级高于逐 profile 层）
├── .env                      # 环境变量（优先级低于调用目录的 .env）
├── settings.yaml             # settings-file 的默认路径
├── .credentials.yaml         # 凭据（credentials-local 的文件层）
├── .anonymous-user-id        # 匿名身份（随机 UUID，不从机器信息派生）
├── sessions/                 # 会话 JSONL 持久化（见第 5 章）
├── storages/                 # storage-json 的 KV 数据
├── attachments/v1/           # 附件（图片等）存储
├── .agent-presets/           # 用户级 agent preset 根（trust: user）
└── profiles/
    ├── node_modules/         # 安装后备：扁平符号链接目录，每次启动 heal
    └── <name>/               # 一个 profile 一个目录
        ├── package.json          # dsh.profile.bundles + 树外插件依赖
        ├── cordis.patch.yml      # 该 profile 的用户 patch 层
        ├── cordis.yml            # 每次启动被重写为空列表（组合结果不烤进文件）
        └── pnpm-workspace.yaml
```

几个值得知道的机制：

- **`profiles/node_modules/` 后备目录**：对 app manifest 的 dependencies + peerDependencies 做 BFS，每个包维护一条扁平符号链接。裸插件 specifier 走 Node 逐级上查时，这保证树外插件总能解析——即使 profile 目录里没跑过 pnpm install。
- **`cordis.yml` 为什么每次被清空**：Loader 会把运行时状态写回配置文件；如果让它写，组合结果就被"烤进"文件，下次启动 patch 层就失去意义。每次重写为空列表，强制每次都从各层重新组合。
- **bundle 双锚点解析**：组合包名先从 dsh 安装目录解析、再从 profile 目录解析——内置组合包永远来自当前安装，不会被 profile 里的同名包顶掉。

## 3.2 配置的三个来源

| 来源 | 形态 | 生效时机 |
|---|---|---|
| 组合层（bundle/patch） | cordis.yml 条目与 patch | 启动时组合；patch 文件热更（见[第 1 章](01-cordis与组装.md)） |
| 用户设置 | `$DSH_HOME/settings.yaml`，经 `ctx.settings` 三层解析（schema 默认 → 组合 base → 用户分节） | 运行时 |
| 凭据 | `ctx.credentials` 引用（不是值！），按操作解析：env / file / project-env / user-env 层 | 每次使用——支持热轮换 |

凭据设计成"引用 ≠ 值"是关键：LLM 适配器等消费方每次操作时重新解析引用，因此轮换 API key 不需要重启；而凭据值从不进入会话日志（模型可见 ⟺ 已记录的反面：**秘密绝不入日志**）。 两条凭据 seam 的硬规则：空的存储值在任何地方都视为不存在；`describe()` 对被进程环境遮蔽的引用报 `writable: false`，直接拒绝"表面成功的写入"。设置 seam 除三层解析外还提供：`applies: 'live'|'restart'`（生效时机）、`validate` 钩子（schema 表达不了的跨字段约束）、`redactSecrets` + `role('secret')`（每个对外接口必须脱敏）、`revision`/`expectedRevision` 乐观并发控制。

## 3.3 环境变量分层

启动时 `loadLayeredEnv`：继承的进程环境 > 调用目录 `.env` > home `.env`。普通业务变量（如 `DEEPSEEK_API_KEY`，e2e 测试与 demo 读它）可以写进 `.env`。但有一类 **bootstrap-only** 变量被拒绝写入 .env 文件——它们必须在进程外设定：所有以 `DSH_`、`XDG_`、`DYLD_`、`BASH_FUNC_` 开头的变量（如 `DSH_HOME`）。

派生 overlay 的例子：`DSH_TELEMETRY_DISABLED` 被启动器翻译成一条 `{id: 'session-telemetry-otel', disabled: true}` patch——任何非空值（含 `'0'`/`'false'`）都禁用，且仅当组合树里实际存在该 telemetry 条目时才生成这条 patch。环境变量与配置树之间通过这个机制打通，而不是在插件里到处读环境变量。

## 3.4 小结

数据落点的设计原则和代码侧一致：**每类数据有一个权威位置，且这个位置是 seam 的实现细节而非硬编码路径**。会话历史在 `sessions/`（由持久化后端拥有）、KV 在 `storages/`（storage 后端拥有）、凭据在凭据 seam 的各层、组合在 profile。换掉任何一个 Provider，落盘位置可以整个改变而消费方无感。下一章进入系统的心脏：核心循环。
