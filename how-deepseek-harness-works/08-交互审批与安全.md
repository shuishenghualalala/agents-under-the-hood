# 第 8 章：交互、审批与纵深防御

> 本章导读：agent 有能力执行 shell 命令、改文件，安全就不能是一道墙，而要是一组各自独立、逐层收紧的机制。本章讲清七层防御各防什么、一次审批的完整生命周期、外部 hook（Claude Code/Codex 生态）如何桥接进来、以及 guard 如何防 agent 自己失控。建议先读[第 7 章](07-工具系统与执行世界.md)（工具流水线与沙箱）。

## 8.1 七层防御全景

| 层 | 机制 | 防什么 | 失败姿态 |
|---|---|---|---|
| L0 模型叙述 | system-prompt 注入审批政策句与沙箱拒绝词汇 | 模型误用（不知道会被拒而反复尝试） | 无强制力，纯对齐 |
| L1 权限预设 | permission-presets 把 `sandbox/mode` + `approval/policy` 打包成一个选择器 | 用户配置错误（两个旋钮不一致） | **不拥有强制力**，只经各 knob 的规范 setter 写入 |
| L2 审批 | `ctx.approval` 逐次操作的人/机决策 | 单次危险操作（提权重试、hook ask） | 闭合拒绝：非 `allowed-once` 一律 deny |
| L3 进程沙箱 | `ctx.sandbox.confine()` 包装 argv | 不可信 shell 命令的文件系统副作用 | `SANDBOX_UNAVAILABLE` 抛错，禁止静默透传 |
| L4 fs 策略 | fs-sandbox 进程内路径栅栏 + 观测策略 | fs 能力自身的 write/edit 突变 | 结构化 `FS_SANDBOX_DENIED` |
| L5 外部 hook | Claude Code/Codex hooks.json 桥 | 部署方自定义策略（组织合规脚本） | hook 跑不起来 = 非阻塞；exit 2 = 阻断 |
| L6 循环卫生 | guard：repeat-tool-reminder + timeout-policy | agent 可用性风险：死循环、挂死工具 | 建议性提醒 / 结构化 TOOL_TIMEOUT 结果 |

要点：**除 guard 外每层都是可选能力 seam**——不组合就 fail-closed 降级（ask 一路落到 deny），而不是裸奔。预设（L1）明言"不拥有任何强制执行"，执行与回放仍读各 knob 的折叠结果——它是防配置错误的便利层，不是第四道墙。

横向卫生（`docs/defensive-patterns.zh.md`）：spawn 环境变量 scrub 掉 `*KEY*|*SECRET|*TOKEN*|*PASSWORD*`；临时文件用 0700 私有目录 + `'wx'` 独占创建；符号链接用 unlink 删除。

## 8.2 审批：核心抽象

`ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'`——**闭合并集，唯一授权是 `allowed-once`**。注意没有 "allow always"：持久授权不存在于词汇表里。

- `ApprovalRequest { agent, toolName, callId?, reason?, signal? }`：有意省略工具参数——UI 用 `callId` 挂到已流式输出的工具调用上（参数已经在日志里，不需要复制进审批请求）。
- `ApprovalPolicy = 'ask' | 'never'`；生效值 = 会话日志最后一条 `approval/policy` 事件，回退到服务配置（默认 `'ask'`）。**回放即状态**。
- 审计对：`approval/asked` + `approval/decided`（仅日志事件，不进模型 transcript），由 branded id 配对。
- 分发：`approval/request` waterfall——应答者返回结果占据决策槽，或 `next()` 委托；scope 过滤使 agent 作用域监听器只收到自己的请求。

## 8.3 一次需要审批的工具调用（完整路径）

以 hook 发出 ask 为例：

```text
1. tools/pre-execute waterfall，默认 {kind:'allow'}
2. Claude Code 桥监听器把调用转成 PreToolUse hook 进程；
   合并结果为 ask → 返回 {kind:'ask', reason}
3. 工具运行时见 ask → ctx.get('approval')：
   服务缺失或无 agent → 直接 deny（机会式消费，fail-closed 降级）
4. ApprovalService.request()：
   · 要求当前在开放轮次内——审计对必须被 turn 的 commit/replay
     边界包住，否则拒绝（官方措辞：idle ask 在追加任何事件前即 reject，不留半截审计）
   · 追加 approval/asked
5. decide()：
   · signal 已中止 → cancelled
   · 政策 'never' → 在服务内部、waterfall 分发之前返回 rejected
     （cordis 允许 prepend 注册，监听器形态的闸门无法给出
     "与注册顺序无关的确定性拒绝"，所以 never 必须在服务路径里）
   · 否则 dispatch approval/request waterfall；
     无应答者 → unavailable；应答者抛异常/返回词表外值 → unavailable；
     signal 与应答竞速，迟到答案丢弃
6. 应答者实例：Web host 把请求转为 mux 上可应答的 server-request
   （倒扫会话事件配对 asked/decided，见 packages/host/apiproxy 源码）；ACP 桥提供一次性机器决策
   （allow-once/reject-once 两选项，绝不从未知响应推断持久授权）
7. 追加 approval/decided；outcome 映射回工具决策：
   allowed-once → allow；rejected/cancelled/unavailable →
   三种措辞不同的 deny——让模型能区分"人说不"与"没有审批通道"
8. deny 以 isError 工具结果呈现给模型
```

**沙箱提权路径**：模型在被拒后带 `sandbox_permissions + justification` 重试 → `approveEscalation()` 先做"严格更宽"执行期检查 → 发审批请求（reason 含目标模式与理由原文）→ 批准的模式只盖在这次调用上，经 `ctx.sandboxPolicy.resolve()` 的显式 mode 覆盖生效。

## 8.4 外部 hook：复用生态而非发明协议

dsh 没有发明自己的 hook API，而是桥接现成的 Claude Code/Codex hooks.json 生态（进程 + stdin/stdout JSON 契约）：

- **方言中立部分**沉到 `dsh-hook-protocol` 库：编解码（exit 2 = block 且 stderr 为理由；exit 0 才把 stdout 当 JSON 解析）、matcher、合并（`deny > ask > allow` 取最严，`continue:false` 粘滞）、执行、detached 生命周期。两个桥各只拥有自己的 payload 与决策映射。
- **hook 进程经 `ctx.shell` 运行**——自动继承凭据 scrub、进程组取消与超时，hook 不会成为凭据泄漏通道。基础设施故障转为"无 exit code 的非阻塞结果"，**runHook 永不抛出**。
- `updatedInput`（hook 改写工具参数）被刻意**解析但不执行**——只告警。
- 每个 hook 写 `hook/invoked` + `hook/result` 审计对。
- 决策映射示例：PreToolUse deny→deny、ask→ask；Stop deny→`agent.steer()` 强制继续（目前无上限，源码自带 TODO(stop-loop-guard)）。

定位明确：定制行为应该写成同样扩展点上的原生类型化插件；hook 桥是为了**复用未修改的既有生态**。

## 8.5 guard：防 agent 自己失控

前两层的威胁模型是"模型做坏事"，guard 的威胁模型是"模型卡住了"：

- **repeat-tool-reminder**：WeakMap 按 agent 跟踪"同名+规范化参数"连续调用链，命中阈值（默认 [3,5,8]）时在 `tools/post-execute` prepend 提醒消息——只 enrich 不否决。**被拒的调用也计数**：模型反复锤一个被拒调用正是要打破的循环。用户插话重置链。
- **timeout-policy**：包装 `tools/execute`，工具声明 `timeoutMs` 才武装 deadline；用自己的 `TOOL_TIMEOUT` code 区分内外层 deadline，自己的定时器胜出才替换为结构化超时结果；`finally` 恢复上游 signal。

## 8.6 其他交互件速记

- **commands**（`ctx.commands`）：用户命令（如 `/feedback`）无需模型轮次即可分派；记录 `command/run`/`command/done`，不产生模型消息。
- **ask-user**（user-questions + tool-ask-user）：模型经 `ask_user_question` 工具向用户提问；单 provider 注册；请求含稳定 id、options、multiSelect、intent。
- **permission presets**：默认表 `workspace-write`（sandbox=workspace-write + approval=ask）与 `danger-full-access`（danger-full-access + never）；`custom` 是派生的"非预设"状态，永不可作为切换目标。
- **identity**：匿名 UUID 存 `$DSH_HOME/.anonymous-user-id`，不从主机名/网络/git remote 派生；只读 home 也返回本次可用 id。
- **schedule**：持久提醒（after/at/every，every ≥300s），唯一权威是会话日志 `schedule/change` 事件；等 agent 完全 idle 后认领 maintenance phase → `followup()` 入队提醒（**绝不 steer、绝不打断当前轮次**）；准入到持久 dispatch 之间有窄崩溃窗口——**至少一次**交付。

## 8.7 设计取舍

**为什么审批是能力而不是 agent-loop 内置分支**：(a) 组合可选——CI/无人值守部署不组合任何应答者甚至不组合服务，ask 一路 fail-closed 到 deny；(b) 应答者开放——waterfall 让 Web UI、ACP 桥、任何插件都能当应答者，决策槽唯一、作用域过滤保证路由；(c) 服务中途卸载也退化为 deny；(d) `never` 的确定性只能靠服务内路径保证。内置 if 分支一条都做不到。

**为什么审计对必须轮次内**：turn 是持久日志的 commit/replay 边界。官方明确 idle ask 在追加任何事件前即 reject；"轮次外的裸事件在重载时与崩溃尾巴不可区分、会被静默丢弃"是本文对此的推断解释。所以 idle 状态的 ask 在追加任何事件之前就抛错——宁可报错，不留半截审计。

## 8.9 小结

安全章的系统模型：**七层独立机制逐层收紧，每层失败姿态明确（fail-closed），审批是闭合结果的能力而非内置分支，外部生态经 wire 协议桥接而非发明新 API，agent 失控由 guard 以数据方式缓解**。下一章离开单 agent 范围：subagent、preset 与其他编排能力。
